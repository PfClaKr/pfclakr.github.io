The [A/B partitions post](/posts/architecture/os/ota-update/ab-partitions/) used U-Boot. On x86 UEFI
machines GRUB usually sits in that spot. The principle is the same: the bootloader has a small state store
it can read and write, recording which slot to try first and whether an attempt is pending. In GRUB that
store is **grubenv**.

This post answers:

- how GRUB finds `grub.cfg` on a normal install, and why that doesn't fit A/B as is;
- where the shared, **primary GRUB** lives and how it chooses a slot;
- how each slot keeps **its own kernel and its own grub.cfg**, and how to change `update-grub` for that.

Everything below was booted for real in QEMU (OVMF UEFI firmware) with an Ubuntu 6.8 kernel. GRUB is
2.12 from Ubuntu 24.04.

## How GRUB finds grub.cfg on a normal install

Installing Debian or Ubuntu on a UEFI machine gives this boot path:

1. The firmware follows an NVRAM boot entry (or the fallback path `\EFI\BOOT\BOOTX64.EFI`) and runs
   `shimx64.efi` and `grubx64.efi` from the ESP (EFI system partition, FAT).
2. GRUB first reads `grub.cfg` from its own ESP directory (e.g. `/EFI/ubuntu`). That file is a
   three-line pointer:

   ```text
   search.fs_uuid 3f1c9e1a-... root
   set prefix=($root)'/boot/grub'
   configfile $prefix/grub.cfg
   ```

3. It moves on to `/boot/grub/grub.cfg` on the filesystem with that UUID, the root filesystem. That is the
   real configuration, generated by `update-grub`.

In an A/B setup this breaks in three places:

- **The pointer names one filesystem.** Switching slots means rewriting a file on the ESP, a write with no
  automatic way back if the new slot doesn't boot.
- **Both slots can have the same UUID.** Image-based updates write the same filesystem image to both
  slots, so `search.fs_uuid` and the `root=UUID=…` that `update-grub` emits both pick whichever copy is
  found first.
- **Packages overwrite the ESP.** Ubuntu's `grub-efi-amd64-signed` re-runs `grub-install` from its postinst
  on upgrade whenever `/boot/grub/x86_64-efi/core.efi` exists. Upgrading packages in slot B rewrites the
  shared ESP's GRUB and pointer in terms of slot B.

## The layout: what is shared, what belongs to a slot

The fix is to split the GRUB configuration into two layers:

```text
ESP (FAT)                   shared; slot updates never touch it
└── EFI/BOOT/
    ├── BOOTX64.EFI         GRUB itself (installed once, rarely changed)
    ├── grub.cfg            the slot chooser
    └── grubenv             ORDER, A_OK, A_TRY, B_OK, B_TRY
rootfs_A (ext4, GPT name rootfs_A)
└── boot/
    ├── vmlinuz-6.8.0-147-generic
    ├── initrd.img-6.8.0-147-generic
    └── grub/grub.cfg       generated by update-grub inside slot A
rootfs_B (ext4, GPT name rootfs_B)
└── boot/ …                 same layout
```

- The **primary GRUB** (ESP) only chooses a slot. It knows nothing about kernels or command lines.
- A **slot's grub.cfg** only boots that slot's kernel. It is updated with the slot, and upgrading the
  kernel inside a slot makes that slot's `update-grub` regenerate its own file and nothing else.
- Slots are identified by **GPT partition name** (`rootfs_A`, `rootfs_B`), not UUID. The name lives in the
  partition table, so writing the same image to both slots doesn't change it.

## grubenv: the only file GRUB can write

GRUB can barely write to disk at all. grubenv is the exception, which explains its odd format:

```bash
grub-editenv grubenv create
grub-editenv grubenv set ORDER="A B" A_OK=1 A_TRY=0
grub-editenv grubenv list
# ORDER=A B
# A_OK=1
# A_TRY=0
wc -c grubenv
# 1024 grubenv
```

```text
# GRUB Environment Block
# WARNING: Do not edit this file by tools other than grub-editenv!!!
ORDER=A B
A_OK=1
A_TRY=0
##########################################…   (# up to 1024 bytes)
```

The fixed 1024-byte size is deliberate. GRUB has no filesystem write support, so `save_env` finds the disk
blocks the file already occupies and **overwrites them in place**. It cannot grow the file or allocate
blocks, so the file is created at a fixed size. For the same reason the filesystem must expose plain block
locations: FAT and ext4 work, while LVM or RAID, btrfs, ZFS and SquashFS are refused (Ubuntu's
`/etc/grub.d/00_header` checks exactly this list). The ESP is FAT, which makes it a good home for grubenv.

On the GRUB side there are two commands:

| Command | Does |
|---|---|
| `load_env [-f file] [var …]` | Reads grubenv into variables. With variable names, only those are read. |
| `save_env [-f file] var …` | Writes the named variables into grubenv. |

Without a file they use `$prefix/grubenv`. `$prefix` is the config directory baked into the GRUB image;
here it is `/EFI/BOOT` on the ESP. From Linux the same file is handled with `grub-editenv file set|unset|list`.

## The primary GRUB: a slot chooser on the ESP

The variable names are the ones RAUC's GRUB backend uses. Each slot has two:

- `X_OK=1`: the slot holds a usable system.
- `X_TRY=1`: a boot of this slot was attempted and hasn't been confirmed good yet.

```bash
# ESP: /EFI/BOOT/grub.cfg -- the only GRUB config that is never part of a slot.
# Picks a slot from grubenv, then hands over to that slot's own grub.cfg.

set ORDER="A B"
set A_OK=0
set A_TRY=0
set B_OK=0
set B_TRY=0
load_env ORDER A_OK A_TRY B_OK B_TRY

set SLOT=
for s in $ORDER; do
  if [ "$s" = A ]; then ok=$A_OK; try=$A_TRY; fi
  if [ "$s" = B ]; then ok=$B_OK; try=$B_TRY; fi
  if [ "$ok" = 1 -a "$try" = 0 ]; then
    SLOT=$s
    break
  fi
done

if [ -z "$SLOT" ]; then
  echo "No bootable slot left"
  sleep 30
  halt
fi

# Spend the slot's one attempt *before* booting it.
if [ "$SLOT" = A ]; then set A_TRY=1; set root=(hd0,gpt2); fi
if [ "$SLOT" = B ]; then set B_TRY=1; set root=(hd0,gpt3); fi
save_env A_TRY B_TRY

echo "ab: ORDER=$ORDER A=$A_OK/$A_TRY B=$B_OK/$B_TRY -> slot $SLOT"
export SLOT
configfile /boot/grub/grub.cfg
```

Line by line:

- **Defaults first, then `load_env`.** If grubenv is empty or a variable is missing, the script still runs
  on known values. Passing a list to `load_env` reads only these five, whatever else grubenv contains.
- **In `ORDER`**, pick the first slot with `OK=1` and `TRY=0`.
- **Save `TRY=1`, then boot.** If the kernel hangs or the power goes, the next boot finds the attempt
  already spent and skips the slot. The slot keeps being chosen only if Linux comes up and sets `TRY=0`.
- **Flags instead of a counter** because GRUB's scripting has no arithmetic: `$((n-1))` is a syntax error,
  and there is neither `expr` nor `setexpr`. A countdown like U-Boot's `BOOT_A_LEFT=3` can't be written
  directly, so the scheme allows a single attempt.
- **Set `root`, then `configfile`.** The slot's partition becomes `root` and its `/boot/grub/grub.cfg` is
  read. `search --label` would work instead of partition numbers, but only if each slot's filesystem label
  differs.

### What `configfile` passes on, and what it doesn't

`configfile` reads the new file in a new context. What crosses over is the crux of this design, so I
checked it with grub-emu:

| | inside the slot's grub.cfg |
|---|---|
| exported variables (`SLOT`) | visible |
| non-exported variables | not visible |
| `root` | the slot partition set by the chooser (exported by default) |
| `prefix` | **still `/EFI/BOOT` on the ESP** |
| `config_directory` | the slot's `/boot/grub` |
| variables changed in the slot | don't come back to the chooser |

The unchanged `$prefix` matters. If the slot's grub.cfg calls `load_env` or `save_env` without a file, it
reads and writes **the ESP's grubenv**, not something in its own directory. That is why the stock
`update-grub` output can't be used as is.

## The slot side: customising update-grub

`update-grub` is a three-line script calling `grub-mkconfig -o /boot/grub/grub.cfg`. `grub-mkconfig` reads
`/etc/default/grub`, runs every **executable** script in `/etc/grub.d/` in name order, and concatenates
their output into grub.cfg. So customising means removing the execute bit from scripts and adding new ones.

The scripts disabled inside the slot image, and why:

| Script | Why it goes |
|---|---|
| `00_header` | Runs `load_env` on `$prefix/grubenv` and `save_env` for `next_entry` and `saved_entry`. Inside a slot `$prefix` is the ESP, so it touches the shared grubenv. |
| `10_linux` | Emits `root=UUID=…` (both slots may share a UUID), and on Ubuntu every entry calls `recordfail`, which does `save_env recordfail`, again into the ESP's grubenv. |
| `30_os-prober` | Finds the other slot as "another operating system" and adds it to the menu. |
| `10_linux_zfs`, `20_linux_xen`, `25_bli`, `30_uefi-firmware` | Of no use here. |

```bash
chmod -x /etc/grub.d/00_header /etc/grub.d/10_linux /etc/grub.d/10_linux_zfs \
         /etc/grub.d/20_linux_xen /etc/grub.d/25_bli /etc/grub.d/30_os-prober \
         /etc/grub.d/30_uefi-firmware
```

And the script that takes `10_linux`'s place:

```sh
#!/bin/sh
# /etc/grub.d/10_ab: replaces 10_linux inside an A/B slot.
# Emits a single entry for the newest kernel in this slot's /boot.
# $SLOT is left for GRUB to expand: the ESP chooser exports it.
set -e
. "$pkgdatadir/grub-mkconfig_lib"

latest=$(ls /boot/vmlinuz-* 2>/dev/null | version_sort -r | head -n 1)
[ -n "$latest" ] || exit 0
version=${latest#/boot/vmlinuz-}

cat <<EOF
set default=0
set timeout=0

menuentry "Linux $version (slot \$SLOT)" {
	linux /boot/vmlinuz-$version root=PARTLABEL=rootfs_\$SLOT ro rauc.slot=\$SLOT ${GRUB_CMDLINE_LINUX}
	initrd /boot/initrd.img-$version
}
EOF
```

- `grub-mkconfig` exports `pkgdatadir`; `version_sort` from `grub-mkconfig_lib` sorts the kernel versions.
- **`\$SLOT` is escaped** so the shell leaves it alone. The generated file contains a literal `$SLOT`, which
  GRUB replaces at boot with the value exported by the chooser. Both slots can therefore carry **the exact
  same grub.cfg** and still boot with the right `root=` and `rauc.slot=`. The image never needs to know
  whether it is A or B.
- `rauc.slot=` is how Linux learns which slot it is running from once it is up; mark-good needs it.
- `root=PARTLABEL=` lets the initramfs find the root filesystem by GPT partition name.

`/etc/default/grub` only keeps the kernel arguments:

```bash
GRUB_CMDLINE_LINUX="console=ttyS0"
```

Running `update-grub` inside the slot then produces this. The output left over from `05_debian_theme`,
`40_custom` and `41_custom` is harmless.

```text
### BEGIN /etc/grub.d/05_debian_theme ###
set menu_color_normal=cyan/blue
set menu_color_highlight=white/blue
### END /etc/grub.d/05_debian_theme ###

### BEGIN /etc/grub.d/10_ab ###
set default=0
set timeout=0

menuentry "Linux 6.8.0-147-generic (slot $SLOT)" {
	linux /boot/vmlinuz-6.8.0-147-generic root=PARTLABEL=rootfs_$SLOT ro rauc.slot=$SLOT console=ttyS0
	initrd /boot/initrd.img-6.8.0-147-generic
}
### END /etc/grub.d/10_ab ###
…
```

### When the kernel is upgraded

Debian-family kernel packages run the hooks in `/etc/kernel/postinst.d/` after installation, and
`zz-update-grub` (from grub2-common) calls `update-grub` if `/boot/grub/grub.cfg` exists. Upgrading the
kernel in slot B puts the new kernel in slot B's `/boot` and regenerates slot B's grub.cfg only. The ESP and
slot A stay as they were.

`grub-common` (grub-mkconfig) and `grub2-common` (update-grub and the kernel hook) are all the GRUB packages
a slot image needs. Packages that run `grub-install` from their postinst, such as `grub-efi-amd64`,
`grub-efi-amd64-signed` and `shim-signed`, stay out of the slots; the ESP's GRUB is installed separately, at
image build or factory time.

### Building the primary GRUB

Without Secure Boot, the ESP's GRUB can be built directly with `grub-mkimage`:

```bash
grub-mkimage -O x86_64-efi -p /EFI/BOOT -o esp/EFI/BOOT/BOOTX64.EFI \
  part_gpt fat ext2 normal configfile loadenv test echo linux gzio sleep halt
cp esp-grub.cfg esp/EFI/BOOT/grub.cfg
grub-editenv esp/EFI/BOOT/grubenv create
grub-editenv esp/EFI/BOOT/grubenv set ORDER="A B" A_OK=1 A_TRY=0 B_OK=0 B_TRY=0
```

`-p /EFI/BOOT` becomes `$prefix`. With no device in it, GRUB uses the device it was started from, the ESP,
so `grub.cfg` and `grubenv` are looked up there. `\EFI\BOOT\BOOTX64.EFI` is the path the firmware finds
without any boot entry, so NVRAM doesn't need to be touched.

With Secure Boot, keep the distribution's signed `shimx64.efi` and `grubx64.efi`, and replace the
`grub.cfg` that GRUB reads first in its ESP directory (the three-line pointer on a normal install) with the
chooser above. Modules can't be added to a signed image, so check that every command the chooser uses is
built into it.

## The Linux side: changing the state

The update agent mounts the ESP (usually at `/boot/efi`) and edits the variables with `grub-editenv`:

| Action | Command |
|---|---|
| Activate slot B after writing a new image to it (mark-active) | `grub-editenv $ENV set ORDER="B A" B_OK=1 B_TRY=0` |
| Confirm the booted slot is healthy (mark-good) | `grub-editenv $ENV set B_OK=1 B_TRY=0` |
| Give up on a slot (mark-bad) | `grub-editenv $ENV set B_OK=0` |

`$ENV` is `/boot/efi/EFI/BOOT/grubenv`, and `rauc.slot=` in `/proc/cmdline` says which slot is running.
mark-good can be called from a systemd unit that runs after a health check, as in the
[RAUC post](/posts/architecture/os/ota-update/rauc/). With RAUC, `bootloader=grub` and a `grubenv=` path in
`system.conf` let RAUC manage the same variables itself.

## Running it in QEMU

I built a disk image with an ESP, `rootfs_A` (release 1.0) and `rootfs_B` (release 2.0) and booted it with
OVMF. The initramfs and root filesystems are minimal busybox setups, and the root's `/sbin/init` prints who
it is and powers off. The `grub-editenv` calls between boots play the update agent.

```text
=== boot 1: factory state (ORDER="A B" A_OK=1)
ab: ORDER=A B A=1/1 B=0/0 -> slot A
rootfs: running release 1.0 from /dev/vda2
### grub-editenv set A_TRY=0                         (mark-good A)
### grub-editenv set ORDER="B A" B_OK=1 B_TRY=0      (update written to B, mark-active B)

=== boot 2: new slot
ab: ORDER=B A A=1/0 B=1/1 -> slot B
rootfs: running release 2.0 from /dev/vda3
    (B's health check failed, so mark-good never ran)

=== boot 3: automatic rollback
ab: ORDER=B A A=1/1 B=1/1 -> slot A
rootfs: running release 1.0 from /dev/vda2
### grub-editenv set A_TRY=0 B_TRY=0                 (mark-good on both A and B)

=== boot 4
ab: ORDER=B A A=1/0 B=1/1 -> slot B
rootfs: running release 2.0 from /dev/vda3
### grub-editenv set A_TRY=1 B_TRY=1

=== boot 5: both slots have spent their attempt
No bootable slot left
```

(The `ab:` line is printed after `TRY` is set to 1, so the chosen slot always shows `/1`.)

In boot 2 GRUB saved `B_TRY=1` and booted B. B rebooted without mark-good, so boot 3 skipped it and came
back to A. `ORDER` still says `B A` at that point: the agent on A can tell the update failed from the fact
that it didn't boot the first slot in `ORDER`, mark B bad and report back.

The kernel command line in boot 3 was `root=PARTLABEL=rootfs_A ro rauc.slot=A console=ttyS0`. Both slots
carry the very same grub.cfg; the `$SLOT` expanded by GRUB is what put the right values in.
