[A/B 파티션 글](/ko/posts/architecture/os/ota-update/ab-partitions/)은 U-Boot 기준이었습니다. x86 UEFI
장비에서는 그 자리에 보통 GRUB이 있습니다. 원리는 같습니다. 부트로더가 읽고 쓸 수 있는 작은 상태
저장소가 있고, 거기에 어느 슬롯을 먼저 시도할지와 시도 횟수를 기록합니다. GRUB에서는 그 저장소가
**grubenv**입니다.

이 글은 다음 질문들에 답합니다.

- 일반 설치에서 GRUB은 어떻게 `grub.cfg`를 찾고, 왜 그대로는 A/B에 맞지 않는가
- 공유되는 **기본 GRUB**은 어디에 두고 어떻게 슬롯을 고르는가
- 각 슬롯은 어떻게 **자기 커널과 자기 grub.cfg**를 유지하는가, 그리고 `update-grub`을 어떻게 바꾸는가

글에 나오는 설정은 모두 QEMU(OVMF UEFI 펌웨어)에서 Ubuntu 6.8 커널로 실제로 부팅해 확인했습니다.
GRUB은 Ubuntu 24.04의 2.12입니다.

## 일반 설치에서 GRUB이 grub.cfg를 찾는 과정

데비안/우분투를 UEFI 장비에 설치하면 부팅 경로는 이렇습니다.

1. 펌웨어가 NVRAM의 부트 엔트리(또는 기본 경로 `\EFI\BOOT\BOOTX64.EFI`)를 따라 ESP(EFI 시스템
   파티션, FAT)에서 `shimx64.efi`와 `grubx64.efi`를 실행합니다.
2. GRUB은 자기가 놓인 ESP 디렉터리(예: `/EFI/ubuntu`)의 `grub.cfg`를 먼저 읽습니다. 이 파일은 세 줄짜리
   연결 고리입니다.

   ```text
   search.fs_uuid 3f1c9e1a-... root
   set prefix=($root)'/boot/grub'
   configfile $prefix/grub.cfg
   ```

3. 그 UUID를 가진 파일시스템, 즉 루트 파일시스템의 `/boot/grub/grub.cfg`로 넘어갑니다. 이 파일이
   `update-grub`이 생성하는 진짜 설정입니다.

A/B 구성에서는 이 구조가 세 군데서 어긋납니다.

- **연결 고리가 한 파일시스템만 가리킵니다.** 슬롯을 바꾸려면 ESP의 파일을 고쳐 써야 하는데, 이것은 부팅
  실패 시 자동으로 되돌릴 방법이 없는 쓰기입니다.
- **두 슬롯의 UUID가 같을 수 있습니다.** 이미지 기반 업데이트는 같은 파일시스템 이미지를 두 슬롯에
  씁니다. 그러면 `search.fs_uuid`도, `update-grub`이 넣는 `root=UUID=…`도 둘 중 아무거나 먼저 찾은 쪽을 고릅니다.
- **패키지가 ESP를 덮어씁니다.** 우분투의 `grub-efi-amd64-signed` 패키지는 `/boot/grub/x86_64-efi/core.efi`가
  있으면 업그레이드할 때 postinst에서 `grub-install`을 다시 실행합니다. 슬롯 B에서 패키지를 업그레이드하면
  공유 ESP의 GRUB과 연결 고리가 슬롯 B 기준으로 다시 써집니다.

## 구조: 공유하는 것과 슬롯마다 갖는 것

해결책은 GRUB 설정을 두 층으로 나누는 것입니다.

```text
ESP (FAT)                   공유. 슬롯 업데이트가 건드리지 않음
└── EFI/BOOT/
    ├── BOOTX64.EFI         GRUB 본체 (한 번 설치하고 거의 바꾸지 않음)
    ├── grub.cfg            슬롯 선택기
    └── grubenv             ORDER, A_OK, A_TRY, B_OK, B_TRY
rootfs_A (ext4, GPT 이름 rootfs_A)
└── boot/
    ├── vmlinuz-6.8.0-147-generic
    ├── initrd.img-6.8.0-147-generic
    └── grub/grub.cfg       슬롯 A 안의 update-grub이 생성
rootfs_B (ext4, GPT 이름 rootfs_B)
└── boot/ …                 같은 구조
```

- **기본 GRUB**(ESP)은 슬롯을 고르는 일만 합니다. 커널이 무엇인지, 커널 명령줄이 무엇인지 모릅니다.
- **슬롯의 grub.cfg**는 그 슬롯의 커널을 부팅하는 일만 합니다. 슬롯과 함께 업데이트되고, 슬롯 안에서
  커널을 업그레이드하면 그 슬롯의 `update-grub`이 자기 파일만 다시 만듭니다.
- 슬롯은 UUID가 아니라 **GPT 파티션 이름**(`rootfs_A`, `rootfs_B`)으로 구분합니다. 파티션 이름은 파티션
  테이블에 있어서, 같은 이미지를 써도 바뀌지 않습니다.

## grubenv: GRUB이 쓸 수 있는 유일한 파일

GRUB은 디스크에 거의 아무것도 쓰지 못합니다. 예외가 grubenv이고, 그래서 형식이 특이합니다.

```bash
grub-editenv grubenv create
grub-editenv grubenv set ORDER="A B" A_OK=1 A_TRY=0
grub-editenv grubenv list
# ORDER=A B
# A_OK=1
# A_TRY=0
wc -c grubenv
# 1024 grubenv
```

```text
# GRUB Environment Block
# WARNING: Do not edit this file by tools other than grub-editenv!!!
ORDER=A B
A_OK=1
A_TRY=0
##########################################…   (1024바이트가 될 때까지 #)
```

크기가 정확히 1024바이트로 고정된 데는 이유가 있습니다. GRUB에는 파일시스템 쓰기 기능이 없어서,
`save_env`는 파일이 이미 차지하고 있는 디스크 블록을 찾아 **그 자리에 덮어씁니다**. 파일 크기를 바꾸거나
새 블록을 할당할 수 없으니 처음부터 고정 크기로 만들어 두는 것입니다. 같은 이유로 블록 위치가 그대로
드러나는 파일시스템이어야 합니다. FAT과 ext4는 되고, LVM·RAID 위나 btrfs, ZFS, SquashFS에서는
쓰기가 막힙니다(우분투 `/etc/grub.d/00_header`가 바로 이 목록으로 쓰기 가능 여부를 검사합니다). ESP는
FAT이니 grubenv를 두기에 알맞습니다.

GRUB 쪽 명령은 두 개입니다.

| 명령 | 하는 일 |
|---|---|
| `load_env [-f 파일] [변수 …]` | grubenv를 읽어 변수로 만듭니다. 변수 이름을 주면 그 변수들만 읽습니다. |
| `save_env [-f 파일] 변수 …` | 지정한 변수들을 grubenv에 씁니다. |

파일을 지정하지 않으면 `$prefix/grubenv`를 씁니다. `$prefix`는 GRUB 이미지에 박혀 있는 설정 디렉터리이고,
이 구성에서는 ESP의 `/EFI/BOOT`입니다. 리눅스에서는 `grub-editenv 파일 set|unset|list`로 같은 파일을 다룹니다.

## 기본 GRUB: ESP의 슬롯 선택기

변수 이름은 RAUC의 GRUB 백엔드가 쓰는 것과 같습니다. 슬롯마다 두 개입니다.

- `X_OK=1`: 슬롯에 쓸 수 있는 시스템이 들어 있다.
- `X_TRY=1`: 이 슬롯으로 부팅을 시도했고 아직 정상이라는 확인을 받지 못했다.

```bash
# ESP: /EFI/BOOT/grub.cfg -- 어느 슬롯에도 속하지 않는 유일한 GRUB 설정.
# grubenv에서 슬롯을 고른 뒤, 그 슬롯의 grub.cfg로 넘긴다.

set ORDER="A B"
set A_OK=0
set A_TRY=0
set B_OK=0
set B_TRY=0
load_env ORDER A_OK A_TRY B_OK B_TRY

set SLOT=
for s in $ORDER; do
  if [ "$s" = A ]; then ok=$A_OK; try=$A_TRY; fi
  if [ "$s" = B ]; then ok=$B_OK; try=$B_TRY; fi
  if [ "$ok" = 1 -a "$try" = 0 ]; then
    SLOT=$s
    break
  fi
done

if [ -z "$SLOT" ]; then
  echo "No bootable slot left"
  sleep 30
  halt
fi

# 부팅하기 *전에* 그 슬롯의 시도 기회를 써 버린다.
if [ "$SLOT" = A ]; then set A_TRY=1; set root=(hd0,gpt2); fi
if [ "$SLOT" = B ]; then set B_TRY=1; set root=(hd0,gpt3); fi
save_env A_TRY B_TRY

echo "ab: ORDER=$ORDER A=$A_OK/$A_TRY B=$B_OK/$B_TRY -> slot $SLOT"
export SLOT
configfile /boot/grub/grub.cfg
```

한 줄씩 보면 이렇습니다.

- **기본값을 먼저 정하고 `load_env`.** grubenv가 비어 있거나 변수가 없어도 스크립트가 정의된 값으로
  동작합니다. `load_env`에 변수 목록을 줘서, grubenv에 다른 변수가 들어 있어도 이 다섯 개만 읽습니다.
- **`ORDER` 순서대로**, `OK=1`이면서 `TRY=0`인 첫 슬롯을 고릅니다.
- **`TRY=1`을 저장한 뒤에 부팅합니다.** 커널이 멈추든 전원이 나가든, 다음 부팅에서 이 슬롯은 이미 기회를
  쓴 상태라 건너뜁니다. 리눅스가 정상적으로 올라와 `TRY=0`으로 되돌려 줘야만 계속 이 슬롯이 선택됩니다.
- **카운터가 아니라 0/1인 이유**는 GRUB 스크립트에 산술 연산이 없기 때문입니다. `$((n-1))`은 문법 오류이고
  `expr`도 `setexpr`도 없습니다. U-Boot의 `BOOT_A_LEFT=3` 같은 카운트다운을 GRUB에서 그대로 만들 수 없어서,
  시도를 한 번만 허용하는 플래그를 씁니다.
- **`root`를 정하고 `configfile`.** 슬롯의 파티션을 `root`로 정하고 그 안의 `/boot/grub/grub.cfg`를 읽습니다.
  파티션 번호 대신 `search --label`을 쓸 수도 있지만, 그러려면 슬롯마다 파일시스템 레이블이 달라야 합니다.

### `configfile`이 넘겨주는 것과 넘겨주지 않는 것

`configfile`은 새 설정 파일을 새 컨텍스트에서 읽습니다. 무엇이 넘어가는지가 이 구조의 핵심이라
grub-emu로 확인했습니다.

| | 슬롯의 grub.cfg 안에서 |
|---|---|
| `export`한 변수 (`SLOT`) | 보입니다 |
| `export`하지 않은 변수 | 안 보입니다 |
| `root` | 선택기에서 정한 슬롯 파티션 (기본으로 export되는 변수) |
| `prefix` | **그대로 ESP의 `/EFI/BOOT`** |
| `config_directory` | 슬롯의 `/boot/grub` |
| 슬롯 안에서 바꾼 변수 | 선택기로 돌아오지 않습니다 |

`$prefix`가 바뀌지 않는다는 점이 중요합니다. 슬롯의 grub.cfg가 `load_env`나 `save_env`를 파일 지정 없이
부르면, 슬롯 자기 디렉터리가 아니라 **ESP의 grubenv**를 읽고 씁니다. 아래에서 기본 `update-grub` 출력을
그대로 쓰면 안 되는 이유가 이것입니다.

## 슬롯 쪽: update-grub 커스텀

`update-grub`은 `grub-mkconfig -o /boot/grub/grub.cfg`를 부르는 세 줄짜리 스크립트입니다. `grub-mkconfig`는
`/etc/default/grub`을 읽은 뒤 `/etc/grub.d/`에서 **실행 권한이 있는** 스크립트를 이름 순서대로 실행하고,
그 출력을 이어 붙여 grub.cfg를 만듭니다. 그래서 커스텀은 스크립트의 실행 권한을 끄고 새 스크립트를
넣는 방식으로 합니다.

슬롯 이미지 안에서 끄는 스크립트와 이유입니다.

| 스크립트 | 끄는 이유 |
|---|---|
| `00_header` | `$prefix/grubenv`를 `load_env`하고 `next_entry`, `saved_entry`를 `save_env`합니다. 슬롯 안에서는 `$prefix`가 ESP라서 공유 grubenv를 건드립니다. |
| `10_linux` | `root=UUID=…`를 넣고(두 슬롯의 UUID가 같을 수 있음), 우분투에서는 엔트리마다 `recordfail`을 불러 `save_env recordfail`을 합니다. 역시 ESP의 grubenv에 씁니다. |
| `30_os-prober` | 다른 슬롯을 "다른 운영체제"로 찾아 메뉴에 넣습니다. |
| `10_linux_zfs`, `20_linux_xen`, `25_bli`, `30_uefi-firmware` | 이 구성에서는 쓸모가 없습니다. |

```bash
chmod -x /etc/grub.d/00_header /etc/grub.d/10_linux /etc/grub.d/10_linux_zfs \
         /etc/grub.d/20_linux_xen /etc/grub.d/25_bli /etc/grub.d/30_os-prober \
         /etc/grub.d/30_uefi-firmware
```

그리고 `10_linux` 자리에 들어갈 스크립트입니다.

```sh
#!/bin/sh
# /etc/grub.d/10_ab: A/B 슬롯 안에서 10_linux를 대신한다.
# 이 슬롯 /boot의 가장 새 커널로 엔트리 하나만 만든다.
# $SLOT은 GRUB이 부팅할 때 펼친다. ESP의 선택기가 export한다.
set -e
. "$pkgdatadir/grub-mkconfig_lib"

latest=$(ls /boot/vmlinuz-* 2>/dev/null | version_sort -r | head -n 1)
[ -n "$latest" ] || exit 0
version=${latest#/boot/vmlinuz-}

cat <<EOF
set default=0
set timeout=0

menuentry "Linux $version (slot \$SLOT)" {
	linux /boot/vmlinuz-$version root=PARTLABEL=rootfs_\$SLOT ro rauc.slot=\$SLOT ${GRUB_CMDLINE_LINUX}
	initrd /boot/initrd.img-$version
}
EOF
```

- `pkgdatadir`는 `grub-mkconfig`가 export해 주고, `grub-mkconfig_lib`에 있는 `version_sort`로 커널 버전을 정렬합니다.
- **`\$SLOT`은 셸에서 펼쳐지지 않게** 백슬래시를 붙였습니다. 생성된 파일에는 `$SLOT`이 글자 그대로 남고,
  부팅할 때 GRUB이 선택기에서 export된 값으로 바꿉니다. 그래서 두 슬롯에 **완전히 같은 grub.cfg**가 들어가도
  각자 올바른 `root=`와 `rauc.slot=`으로 부팅합니다. 이미지가 자기가 A인지 B인지 몰라도 됩니다.
- `rauc.slot=`은 리눅스가 올라온 뒤 자기가 어느 슬롯인지 알아내는 수단입니다. mark-good을 할 때 필요합니다.
- `root=PARTLABEL=`은 initramfs가 GPT 파티션 이름으로 루트를 찾게 합니다.

`/etc/default/grub`에는 커널 인자만 둡니다.

```bash
GRUB_CMDLINE_LINUX="console=ttyS0"
```

이 상태로 슬롯 안에서 `update-grub`을 실행하면 이런 파일이 나옵니다. 남아 있는 `05_debian_theme`,
`40_custom`, `41_custom`의 출력은 해가 없습니다.

```text
### BEGIN /etc/grub.d/05_debian_theme ###
set menu_color_normal=cyan/blue
set menu_color_highlight=white/blue
### END /etc/grub.d/05_debian_theme ###

### BEGIN /etc/grub.d/10_ab ###
set default=0
set timeout=0

menuentry "Linux 6.8.0-147-generic (slot $SLOT)" {
	linux /boot/vmlinuz-6.8.0-147-generic root=PARTLABEL=rootfs_$SLOT ro rauc.slot=$SLOT console=ttyS0
	initrd /boot/initrd.img-6.8.0-147-generic
}
### END /etc/grub.d/10_ab ###
…
```

### 커널을 업그레이드하면

데비안 계열의 커널 패키지는 설치 후 `/etc/kernel/postinst.d/`의 훅을 실행하고, 그중
`zz-update-grub`(grub2-common 패키지)이 `/boot/grub/grub.cfg`가 있으면 `update-grub`을 부릅니다. 슬롯 B에서
커널을 업그레이드하면 슬롯 B의 `/boot`에 새 커널이 들어가고 슬롯 B의 grub.cfg만 다시 만들어집니다. ESP와
슬롯 A는 그대로입니다.

:::tip
슬롯 이미지에 넣을 GRUB 패키지는 `grub-common`(grub-mkconfig)과 `grub2-common`(update-grub, 커널 훅)이면
충분합니다. `grub-efi-amd64`, `grub-efi-amd64-signed`, `shim-signed`처럼 postinst에서 `grub-install`을 하는
패키지는 슬롯에 넣지 않습니다. ESP의 GRUB은 이미지 빌드나 공장 설치 단계에서 따로 설치합니다.
:::

### 기본 GRUB 만들기

시큐어 부트를 쓰지 않는다면 ESP용 GRUB은 `grub-mkimage`로 직접 만들 수 있습니다.

```bash
grub-mkimage -O x86_64-efi -p /EFI/BOOT -o esp/EFI/BOOT/BOOTX64.EFI \
  part_gpt fat ext2 normal configfile loadenv test echo linux gzio sleep halt
cp esp-grub.cfg esp/EFI/BOOT/grub.cfg
grub-editenv esp/EFI/BOOT/grubenv create
grub-editenv esp/EFI/BOOT/grubenv set ORDER="A B" A_OK=1 A_TRY=0 B_OK=0 B_TRY=0
```

`-p /EFI/BOOT`가 `$prefix`가 됩니다. 장치를 생략하면 GRUB이 실행된 장치, 즉 ESP가 기준이라 `grub.cfg`와
`grubenv`를 ESP에서 찾습니다. `\EFI\BOOT\BOOTX64.EFI`는 펌웨어가 부트 엔트리 없이도 찾는 기본 경로라서
NVRAM을 건드리지 않아도 됩니다.

:::note 시큐어 부트
시큐어 부트에서는 배포판이 서명한 `shimx64.efi`와 `grubx64.efi`를 그대로 쓰고, 그 GRUB이 처음 읽는 ESP
디렉터리의 `grub.cfg`(일반 설치에서 세 줄짜리 연결 고리가 있던 파일)를 위의 선택기로 바꿉니다. 서명된
이미지에 모듈을 추가할 수 없으니 선택기가 쓰는 명령이 그 이미지에 들어 있는지 확인해야 합니다.
:::

## 리눅스 쪽: 상태 바꾸기

업데이트 에이전트는 ESP를 마운트하고(보통 `/boot/efi`) `grub-editenv`로 변수를 바꿉니다.

| 동작 | 명령 |
|---|---|
| 슬롯 B에 새 이미지를 쓴 뒤 활성화 (mark-active) | `grub-editenv $ENV set ORDER="B A" B_OK=1 B_TRY=0` |
| 부팅한 슬롯이 정상임을 확인 (mark-good) | `grub-editenv $ENV set B_OK=1 B_TRY=0` |
| 슬롯을 버림 (mark-bad) | `grub-editenv $ENV set B_OK=0` |

`$ENV`는 `/boot/efi/EFI/BOOT/grubenv`입니다. 지금 어느 슬롯인지는 `/proc/cmdline`의 `rauc.slot=`으로 압니다.
mark-good은 [RAUC 글](/ko/posts/architecture/os/ota-update/rauc/)에서처럼 헬스 체크를 통과한 뒤 실행되는
systemd 유닛에서 부르면 됩니다. RAUC를 쓴다면 `system.conf`에 `bootloader=grub`과 `grubenv=` 경로를 주면
RAUC가 같은 변수를 직접 관리합니다.

## QEMU에서 돌려 본 결과

ESP, `rootfs_A`(release 1.0), `rootfs_B`(release 2.0)로 디스크 이미지를 만들고 OVMF로 부팅했습니다.
initramfs와 루트 파일시스템은 busybox로 만든 최소 구성이고, 루트의 `/sbin/init`은 자기가 누구인지 출력하고
전원을 끕니다. 부팅 사이의 `grub-editenv`는 업데이트 에이전트 역할입니다.

```text
=== 부팅 1: 공장 상태 (ORDER="A B" A_OK=1)
ab: ORDER=A B A=1/1 B=0/0 -> slot A
rootfs: running release 1.0 from /dev/vda2
### grub-editenv set A_TRY=0                         (mark-good A)
### grub-editenv set ORDER="B A" B_OK=1 B_TRY=0      (B에 업데이트 후 mark-active B)

=== 부팅 2: 새 슬롯
ab: ORDER=B A A=1/0 B=1/1 -> slot B
rootfs: running release 2.0 from /dev/vda3
    (B의 헬스 체크가 실패해서 mark-good을 하지 못함)

=== 부팅 3: 자동 롤백
ab: ORDER=B A A=1/1 B=1/1 -> slot A
rootfs: running release 1.0 from /dev/vda2
### grub-editenv set A_TRY=0 B_TRY=0                 (A, B 모두 mark-good)

=== 부팅 4
ab: ORDER=B A A=1/0 B=1/1 -> slot B
rootfs: running release 2.0 from /dev/vda3
### grub-editenv set A_TRY=1 B_TRY=1

=== 부팅 5: 두 슬롯 모두 시도 기회를 쓴 상태
No bootable slot left
```

:::note
`ab:` 줄의 숫자는 `TRY`를 1로 바꾼 뒤에 출력해서, 선택된 슬롯은 항상 `/1`로 보입니다.
:::

부팅 2에서 GRUB은 `B_TRY=1`을 저장하고 B를 부팅했습니다. B가 mark-good을 하지 못한 채 재부팅되자
부팅 3에서는 B를 건너뛰고 A로 돌아왔습니다. 이때 `ORDER`는 여전히 `B A`입니다. 다시 올라온 A의 에이전트는
"`ORDER`의 첫 슬롯이 아닌 곳에서 부팅됐다"는 사실로 업데이트 실패를 알아차리고, B를 mark-bad 하고 서버에
보고하면 됩니다.

부팅 3에서 커널 명령줄은 `root=PARTLABEL=rootfs_A ro rauc.slot=A console=ttyS0`였습니다. 두 슬롯의
grub.cfg는 똑같은 파일인데도 GRUB이 펼친 `$SLOT` 덕분에 각자 맞는 값이 들어갔습니다.
