L'[article sur les partitions A/B](/fr/posts/architecture/os/ota-update/ab-partitions/) s'appuyait sur
U-Boot. Sur les machines x86 UEFI, c'est généralement GRUB qui occupe cette place. Le principe est le même :
le chargeur d'amorçage dispose d'un petit espace d'état qu'il peut lire et écrire, où l'on note quel slot
essayer en premier et si une tentative est en cours. Chez GRUB, cet espace s'appelle **grubenv**.

Cet article répond aux questions suivantes :

- comment GRUB trouve `grub.cfg` sur une installation normale, et pourquoi cela ne convient pas tel quel à l'A/B ;
- où placer le **GRUB principal**, partagé, et comment il choisit un slot ;
- comment chaque slot garde **son propre noyau et son propre grub.cfg**, et comment adapter `update-grub`.

Tout ce qui suit a réellement démarré dans QEMU (micrologiciel UEFI OVMF) avec un noyau Ubuntu 6.8. GRUB
est la version 2.12 d'Ubuntu 24.04.

## Comment GRUB trouve grub.cfg sur une installation normale

Une installation de Debian ou d'Ubuntu sur une machine UEFI donne ce chemin de démarrage :

1. Le micrologiciel suit une entrée de démarrage de la NVRAM (ou le chemin par défaut
   `\EFI\BOOT\BOOTX64.EFI`) et lance `shimx64.efi` puis `grubx64.efi` depuis l'ESP (partition système EFI, FAT).
2. GRUB lit d'abord le `grub.cfg` de son propre répertoire sur l'ESP (par exemple `/EFI/ubuntu`). Ce fichier
   est un relais de trois lignes :

   ```text
   search.fs_uuid 3f1c9e1a-... root
   set prefix=($root)'/boot/grub'
   configfile $prefix/grub.cfg
   ```

3. Il passe ensuite au `/boot/grub/grub.cfg` du système de fichiers portant cet UUID, la racine. C'est la
   vraie configuration, générée par `update-grub`.

Avec des slots A/B, cela coince à trois endroits :

- **Le relais ne désigne qu'un système de fichiers.** Changer de slot oblige à réécrire un fichier de l'ESP,
  une écriture sans retour automatique si le nouveau slot ne démarre pas.
- **Les deux slots peuvent avoir le même UUID.** Les mises à jour par image écrivent la même image de
  système de fichiers dans les deux slots : `search.fs_uuid` comme le `root=UUID=…` ajouté par `update-grub`
  prennent la première copie trouvée.
- **Les paquets réécrivent l'ESP.** Le paquet `grub-efi-amd64-signed` d'Ubuntu relance `grub-install` depuis
  son postinst lors d'une mise à niveau dès que `/boot/grub/x86_64-efi/core.efi` existe. Mettre à niveau des
  paquets dans le slot B réécrit le GRUB et le relais de l'ESP partagée en fonction du slot B.

## L'organisation : ce qui est partagé, ce qui appartient à un slot

La solution consiste à séparer la configuration de GRUB en deux niveaux :

```text
ESP (FAT)                   partagée ; les mises à jour de slot n'y touchent pas
└── EFI/BOOT/
    ├── BOOTX64.EFI         GRUB lui-même (installé une fois, rarement modifié)
    ├── grub.cfg            le sélecteur de slot
    └── grubenv             ORDER, A_OK, A_TRY, B_OK, B_TRY
rootfs_A (ext4, nom GPT rootfs_A)
└── boot/
    ├── vmlinuz-6.8.0-147-generic
    ├── initrd.img-6.8.0-147-generic
    └── grub/grub.cfg       généré par update-grub dans le slot A
rootfs_B (ext4, nom GPT rootfs_B)
└── boot/ …                 même organisation
```

- Le **GRUB principal** (ESP) ne fait que choisir un slot. Il ne sait rien des noyaux ni des lignes de commande.
- Le **grub.cfg d'un slot** ne fait que démarrer le noyau de ce slot. Il est mis à jour avec le slot, et
  mettre à niveau le noyau dans un slot fait régénérer par son `update-grub` son propre fichier, et rien d'autre.
- Les slots sont identifiés par **nom de partition GPT** (`rootfs_A`, `rootfs_B`), pas par UUID. Le nom est
  stocké dans la table des partitions : écrire la même image dans les deux slots ne le change pas.

## grubenv : le seul fichier que GRUB sait écrire

GRUB ne sait presque rien écrire sur le disque. grubenv est l'exception, d'où son format étrange :

```bash
grub-editenv grubenv create
grub-editenv grubenv set ORDER="A B" A_OK=1 A_TRY=0
grub-editenv grubenv list
# ORDER=A B
# A_OK=1
# A_TRY=0
wc -c grubenv
# 1024 grubenv
```

```text
# GRUB Environment Block
# WARNING: Do not edit this file by tools other than grub-editenv!!!
ORDER=A B
A_OK=1
A_TRY=0
##########################################…   (des # jusqu'à 1024 octets)
```

La taille fixe de 1024 octets est voulue. GRUB n'a pas d'écriture de système de fichiers : `save_env`
retrouve les blocs que le fichier occupe déjà sur le disque et **les écrase sur place**. Il ne peut ni
agrandir le fichier ni allouer de blocs, donc le fichier est créé à taille fixe. Pour la même raison, le
système de fichiers doit exposer des emplacements de blocs simples : FAT et ext4 conviennent, alors que
LVM ou RAID, btrfs, ZFS et SquashFS sont refusés (le `/etc/grub.d/00_header` d'Ubuntu vérifie précisément
cette liste). L'ESP est en FAT, ce qui en fait un bon emplacement pour grubenv.

Côté GRUB, il y a deux commandes :

| Commande | Effet |
|---|---|
| `load_env [-f fichier] [var …]` | Lit grubenv et en fait des variables. Avec des noms de variables, seules celles-ci sont lues. |
| `save_env [-f fichier] var …` | Écrit les variables nommées dans grubenv. |

Sans fichier, elles utilisent `$prefix/grubenv`. `$prefix` est le répertoire de configuration intégré à
l'image GRUB ; ici, `/EFI/BOOT` sur l'ESP. Depuis Linux, on manipule le même fichier avec
`grub-editenv fichier set|unset|list`.

## Le GRUB principal : un sélecteur de slot sur l'ESP

Les noms de variables sont ceux du backend GRUB de RAUC. Chaque slot en a deux :

- `X_OK=1` : le slot contient un système utilisable.
- `X_TRY=1` : un démarrage de ce slot a été tenté et n'a pas encore été confirmé.

```bash
# ESP : /EFI/BOOT/grub.cfg -- la seule config GRUB qui n'appartient à aucun slot.
# Choisit un slot d'après grubenv, puis passe la main au grub.cfg de ce slot.

set ORDER="A B"
set A_OK=0
set A_TRY=0
set B_OK=0
set B_TRY=0
load_env ORDER A_OK A_TRY B_OK B_TRY

set SLOT=
for s in $ORDER; do
  if [ "$s" = A ]; then ok=$A_OK; try=$A_TRY; fi
  if [ "$s" = B ]; then ok=$B_OK; try=$B_TRY; fi
  if [ "$ok" = 1 -a "$try" = 0 ]; then
    SLOT=$s
    break
  fi
done

if [ -z "$SLOT" ]; then
  echo "No bootable slot left"
  sleep 30
  halt
fi

# Consommer la tentative du slot *avant* de le démarrer.
if [ "$SLOT" = A ]; then set A_TRY=1; set root=(hd0,gpt2); fi
if [ "$SLOT" = B ]; then set B_TRY=1; set root=(hd0,gpt3); fi
save_env A_TRY B_TRY

echo "ab: ORDER=$ORDER A=$A_OK/$A_TRY B=$B_OK/$B_TRY -> slot $SLOT"
export SLOT
configfile /boot/grub/grub.cfg
```

Ligne par ligne :

- **Valeurs par défaut d'abord, puis `load_env`.** Si grubenv est vide ou qu'il manque une variable, le
  script fonctionne quand même sur des valeurs connues. Passer une liste à `load_env` ne lit que ces cinq
  variables, quel que soit le reste du contenu de grubenv.
- **Dans l'ordre de `ORDER`**, prendre le premier slot avec `OK=1` et `TRY=0`.
- **Enregistrer `TRY=1`, puis démarrer.** Si le noyau se bloque ou que le courant coupe, le démarrage
  suivant trouve la tentative déjà consommée et saute le slot. Le slot n'est choisi à nouveau que si Linux
  démarre et remet `TRY=0`.
- **Des drapeaux plutôt qu'un compteur**, parce que le langage de script de GRUB n'a pas d'arithmétique :
  `$((n-1))` est une erreur de syntaxe, et il n'y a ni `expr` ni `setexpr`. Un compte à rebours comme le
  `BOOT_A_LEFT=3` d'U-Boot ne s'écrit pas directement, donc le schéma n'autorise qu'une tentative.
- **Fixer `root`, puis `configfile`.** La partition du slot devient `root` et son `/boot/grub/grub.cfg` est
  lu. `search --label` fonctionnerait à la place des numéros de partition, à condition que l'étiquette du
  système de fichiers diffère d'un slot à l'autre.

### Ce que `configfile` transmet, et ce qu'il ne transmet pas

`configfile` lit le nouveau fichier dans un nouveau contexte. Ce qui passe d'un côté à l'autre est le cœur
de cette architecture, je l'ai donc vérifié avec grub-emu :

| | dans le grub.cfg du slot |
|---|---|
| variables exportées (`SLOT`) | visibles |
| variables non exportées | invisibles |
| `root` | la partition du slot fixée par le sélecteur (exportée par défaut) |
| `prefix` | **toujours `/EFI/BOOT` sur l'ESP** |
| `config_directory` | le `/boot/grub` du slot |
| variables modifiées dans le slot | ne reviennent pas au sélecteur |

Le `$prefix` inchangé est important. Si le grub.cfg du slot appelle `load_env` ou `save_env` sans fichier,
il lit et écrit **le grubenv de l'ESP**, pas un fichier de son propre répertoire. C'est pourquoi la sortie
standard d'`update-grub` ne peut pas être utilisée telle quelle.

## Côté slot : personnaliser update-grub

`update-grub` est un script de trois lignes qui appelle `grub-mkconfig -o /boot/grub/grub.cfg`.
`grub-mkconfig` lit `/etc/default/grub`, exécute dans l'ordre des noms chaque script **exécutable** de
`/etc/grub.d/` et concatène leur sortie dans grub.cfg. Personnaliser revient donc à retirer le droit
d'exécution à certains scripts et à en ajouter.

Les scripts désactivés dans l'image du slot, et pourquoi :

| Script | Raison |
|---|---|
| `00_header` | Fait `load_env` sur `$prefix/grubenv` et `save_env` de `next_entry` et `saved_entry`. Dans un slot, `$prefix` est l'ESP : il touche au grubenv partagé. |
| `10_linux` | Produit `root=UUID=…` (les deux slots peuvent partager un UUID) et, sous Ubuntu, chaque entrée appelle `recordfail`, qui fait `save_env recordfail`, là encore dans le grubenv de l'ESP. |
| `30_os-prober` | Détecte l'autre slot comme « un autre système d'exploitation » et l'ajoute au menu. |
| `10_linux_zfs`, `20_linux_xen`, `25_bli`, `30_uefi-firmware` | Inutiles ici. |

```bash
chmod -x /etc/grub.d/00_header /etc/grub.d/10_linux /etc/grub.d/10_linux_zfs \
         /etc/grub.d/20_linux_xen /etc/grub.d/25_bli /etc/grub.d/30_os-prober \
         /etc/grub.d/30_uefi-firmware
```

Et le script qui prend la place de `10_linux` :

```sh
#!/bin/sh
# /etc/grub.d/10_ab : remplace 10_linux dans un slot A/B.
# Produit une seule entrée pour le noyau le plus récent du /boot de ce slot.
# $SLOT est laissé à GRUB : le sélecteur de l'ESP l'exporte.
set -e
. "$pkgdatadir/grub-mkconfig_lib"

latest=$(ls /boot/vmlinuz-* 2>/dev/null | version_sort -r | head -n 1)
[ -n "$latest" ] || exit 0
version=${latest#/boot/vmlinuz-}

cat <<EOF
set default=0
set timeout=0

menuentry "Linux $version (slot \$SLOT)" {
	linux /boot/vmlinuz-$version root=PARTLABEL=rootfs_\$SLOT ro rauc.slot=\$SLOT ${GRUB_CMDLINE_LINUX}
	initrd /boot/initrd.img-$version
}
EOF
```

- `grub-mkconfig` exporte `pkgdatadir` ; `version_sort`, fourni par `grub-mkconfig_lib`, trie les versions de noyau.
- **`\$SLOT` est échappé** pour que le shell n'y touche pas. Le fichier généré contient un `$SLOT` littéral,
  que GRUB remplace au démarrage par la valeur exportée par le sélecteur. Les deux slots peuvent donc
  contenir **exactement le même grub.cfg** et démarrer quand même avec le bon `root=` et le bon
  `rauc.slot=`. L'image n'a jamais besoin de savoir si elle est A ou B.
- `rauc.slot=` permet à Linux, une fois démarré, de savoir depuis quel slot il tourne ; mark-good en a besoin.
- `root=PARTLABEL=` permet à l'initramfs de trouver la racine par nom de partition GPT.

`/etc/default/grub` ne garde que les arguments du noyau :

```bash
GRUB_CMDLINE_LINUX="console=ttyS0"
```

Lancer `update-grub` dans le slot produit alors ceci. La sortie restante de `05_debian_theme`, `40_custom`
et `41_custom` est sans effet gênant.

```text
### BEGIN /etc/grub.d/05_debian_theme ###
set menu_color_normal=cyan/blue
set menu_color_highlight=white/blue
### END /etc/grub.d/05_debian_theme ###

### BEGIN /etc/grub.d/10_ab ###
set default=0
set timeout=0

menuentry "Linux 6.8.0-147-generic (slot $SLOT)" {
	linux /boot/vmlinuz-6.8.0-147-generic root=PARTLABEL=rootfs_$SLOT ro rauc.slot=$SLOT console=ttyS0
	initrd /boot/initrd.img-6.8.0-147-generic
}
### END /etc/grub.d/10_ab ###
…
```

### Quand le noyau est mis à niveau

Les paquets de noyau de la famille Debian exécutent après installation les hooks de
`/etc/kernel/postinst.d/`, et `zz-update-grub` (du paquet grub2-common) appelle `update-grub` si
`/boot/grub/grub.cfg` existe. Mettre à niveau le noyau dans le slot B place le nouveau noyau dans le
`/boot` du slot B et ne régénère que le grub.cfg du slot B. L'ESP et le slot A restent intacts.

`grub-common` (grub-mkconfig) et `grub2-common` (update-grub et le hook du noyau) sont les seuls paquets
GRUB nécessaires dans une image de slot. Les paquets qui lancent `grub-install` depuis leur postinst, comme
`grub-efi-amd64`, `grub-efi-amd64-signed` et `shim-signed`, restent en dehors des slots ; le GRUB de l'ESP
est installé à part, lors de la construction de l'image ou en usine.

### Construire le GRUB principal

Sans Secure Boot, le GRUB de l'ESP se construit directement avec `grub-mkimage` :

```bash
grub-mkimage -O x86_64-efi -p /EFI/BOOT -o esp/EFI/BOOT/BOOTX64.EFI \
  part_gpt fat ext2 normal configfile loadenv test echo linux gzio sleep halt
cp esp-grub.cfg esp/EFI/BOOT/grub.cfg
grub-editenv esp/EFI/BOOT/grubenv create
grub-editenv esp/EFI/BOOT/grubenv set ORDER="A B" A_OK=1 A_TRY=0 B_OK=0 B_TRY=0
```

`-p /EFI/BOOT` devient `$prefix`. Sans périphérique indiqué, GRUB utilise celui depuis lequel il a été
lancé, l'ESP : c'est là qu'il cherche `grub.cfg` et `grubenv`. `\EFI\BOOT\BOOTX64.EFI` est le chemin que le
micrologiciel trouve sans aucune entrée de démarrage, donc inutile de toucher à la NVRAM.

Avec Secure Boot, on garde les `shimx64.efi` et `grubx64.efi` signés de la distribution et on remplace le
`grub.cfg` que ce GRUB lit en premier dans son répertoire de l'ESP (le relais de trois lignes d'une
installation normale) par le sélecteur ci-dessus. On ne peut pas ajouter de modules à une image signée :
il faut vérifier que chaque commande du sélecteur y est intégrée.

## Côté Linux : changer l'état

L'agent de mise à jour monte l'ESP (en général sur `/boot/efi`) et modifie les variables avec `grub-editenv` :

| Action | Commande |
|---|---|
| Activer le slot B après y avoir écrit une nouvelle image (mark-active) | `grub-editenv $ENV set ORDER="B A" B_OK=1 B_TRY=0` |
| Confirmer que le slot démarré est sain (mark-good) | `grub-editenv $ENV set B_OK=1 B_TRY=0` |
| Abandonner un slot (mark-bad) | `grub-editenv $ENV set B_OK=0` |

`$ENV` vaut `/boot/efi/EFI/BOOT/grubenv`, et `rauc.slot=` dans `/proc/cmdline` indique le slot en cours.
mark-good peut être appelé depuis une unité systemd lancée après une vérification de santé, comme dans
l'[article sur RAUC](/fr/posts/architecture/os/ota-update/rauc/). Avec RAUC, `bootloader=grub` et un chemin
`grubenv=` dans `system.conf` lui permettent de gérer lui-même ces variables.

## L'exécution dans QEMU

J'ai construit une image disque avec une ESP, `rootfs_A` (release 1.0) et `rootfs_B` (release 2.0), puis
je l'ai démarrée avec OVMF. L'initramfs et les systèmes de fichiers racine sont des configurations busybox
minimales, et le `/sbin/init` de la racine affiche son identité puis éteint la machine. Les appels à
`grub-editenv` entre les démarrages jouent le rôle de l'agent de mise à jour.

```text
=== démarrage 1 : état d'usine (ORDER="A B" A_OK=1)
ab: ORDER=A B A=1/1 B=0/0 -> slot A
rootfs: running release 1.0 from /dev/vda2
### grub-editenv set A_TRY=0                         (mark-good A)
### grub-editenv set ORDER="B A" B_OK=1 B_TRY=0      (mise à jour écrite dans B, mark-active B)

=== démarrage 2 : nouveau slot
ab: ORDER=B A A=1/0 B=1/1 -> slot B
rootfs: running release 2.0 from /dev/vda3
    (la vérification de santé de B a échoué : pas de mark-good)

=== démarrage 3 : retour arrière automatique
ab: ORDER=B A A=1/1 B=1/1 -> slot A
rootfs: running release 1.0 from /dev/vda2
### grub-editenv set A_TRY=0 B_TRY=0                 (mark-good sur A et B)

=== démarrage 4
ab: ORDER=B A A=1/0 B=1/1 -> slot B
rootfs: running release 2.0 from /dev/vda3
### grub-editenv set A_TRY=1 B_TRY=1

=== démarrage 5 : les deux slots ont consommé leur tentative
No bootable slot left
```

(La ligne `ab:` est affichée après le passage de `TRY` à 1 : le slot choisi apparaît donc toujours avec `/1`.)

Au démarrage 2, GRUB a enregistré `B_TRY=1` et démarré B. B a redémarré sans mark-good, donc le démarrage 3
l'a sauté et est revenu sur A. `ORDER` vaut encore `B A` à ce moment : l'agent sur A peut déduire l'échec de
la mise à jour du fait qu'il n'a pas démarré le premier slot de `ORDER`, marquer B comme mauvais et le signaler.

La ligne de commande du noyau au démarrage 3 était `root=PARTLABEL=rootfs_A ro rauc.slot=A console=ttyS0`.
Les deux slots portent exactement le même grub.cfg ; c'est le `$SLOT` développé par GRUB qui y a mis les
bonnes valeurs.
